# Round four — conditions, recorded before the arm runs

One arm. The treatment is **the written register in the prompt instead of behind a query.**

## What is fixed

| | |
|---|---|
| deployment | `vcptcore-stable` |
| corpus | frozen at the commit this page lands on; 78 active written entries, 3 flows, 590 derived |
| settings | `measurements/kb-comparison-2026-09/arena-settings/settings.arm-c-catalog.json` |
| brief | `BRIEF-arm-C-catalog.md`, generated by `make-brief.mjs` from the corpus, ~5,100 tokens |
| task | `TASK.md`, on `/api/pricing` |
| sealed prediction | `SEALED-RELEVANCE.md`, written before the arm starts |

**The treatment is one line of diff.** Against `settings.arm-c.json`, ignoring the log path, the
only difference is `KB_RETRIEVAL_OFF=1`. Verify it with `diff`, not with this sentence — the arm-C
file carries a comment saying exactly that, and that comment was false for two rounds.

## The four conditions the second review set, and how each is met

**1. The oracle is not drawn from the corpus.** `pick-task.mjs` reads the published REST contract and
all 22 archived tool logs, asks which namespaces no run has ever walked, and never opens `captured/`.
`/api/pricing` came out first at 16 routes. The previous rounds did the opposite: `ORACLE-EXPLAIN.md`
opens with *"Coverage, measured before writing the task"* and maps each item to the entry that
answers it, which made every armless "rediscovery" commissioned. Relevance is **sealed in advance**
in `SEALED-RELEVANCE.md` and scored mechanically afterwards.

**2. The protocol changes for `confirmed` entries.** The brief says an entry with two or more
independent confirmations, not disputed, **may be acted on and cited without re-verification**. One
confirmation, or disputed, is a lead and gets verified. Without this the run repeats the review's
finding 7: round three arm C asked at call 2, was served `KB-27B4CD10`, and then spent six source
calls establishing it anyway — rational under the old protocol, and it makes a call-count result
impossible by construction.

**3. Position and section of every open are recorded.** `score-opens.mjs` reads them out of the kb
journal and the tool log afterwards. `kb show <id>` was added so an open is an event rather than
something parsed out of shell commands.

**4. The arrival hook is off.** One treatment per run. Its three filters are measured in
`kb-arrival-2026-09/addressing.mjs` and deliberately **not built** before this run: building a
mechanism on top of a structure the run may reject is how the last three days went.

## What this run can show, and what it cannot

It can show whether a reader who can see the whole register uses it. It cannot show a capability
difference, because there is no control arm: n = 1, one task, and the three previous rounds already
established that call counts do not move. Comparing this to them would be comparing across tasks.

## The stopping rule, stated before the result exists

> **The frame fails if the arm opens zero catalog entries, or opens them and re-establishes each one
> from scratch anyway.**

If that happens, the conclusion is that a corpus of this shape does not beat an agent with a browser
and a source MCP, and it gets written down that way. The one thing that will not happen is the rule
being adjusted after the number is known.

## What is expected to be uncomfortable

The register holds **nothing** about price lists, assignments or price evaluation — the task is set
on ground it does not cover, on purpose. So the likely honest outcome is a small number of opens, a
report that says the register did not help here, and one or two new entries written. That is a
result, and `SEALED-RELEVANCE.md` predicts it in those words rather than after the fact.
